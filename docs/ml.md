# Machine Learning in AEGIS, Explained from Zero

> Code:
> - `backend/app/ml/features.py`, `backend/app/ml/detector.py`;
> - `ml/synthetic.py`, `ml/train.py`.
>
> Numbers: [ml-evaluation.md](ml-evaluation.md), generated by the training script and never edited by hand.

## 1. Why ML at all, when we have rules?

Rules catch what someone **thought of** ("5 failed logins in 5 minutes"). Attackers adapt: 4 failed logins, 3 denied
requests and a burst of unusual pages each stay **under** every rule, yet together they are clearly odd.

**Anomaly detection** learns what *normal* looks like and flags what is far from it, without anyone writing the rule.
The price: it's statistical. It can be wrong, and its "why" is fuzzier. So in AEGIS ML is **an extra signal**,
never the only one, and every ML detection is labelled `ML` with its score and model version.

## 2. The pipeline

```text
 synthetic events ──► cut into 10-min windows ──► features (8 numbers) ──► Isolation Forest + z-scores
  (ml/synthetic.py)    (SAME code as live)         (app/ml/features.py)       trained on NORMAL only
                                                                                        │
                                       thresholds chosen on validation data ◄──────────┘
                                                        │
                    evaluation on untouched test data ──┴──► model file + metadata + report
```

### Step 1: Data
- We have no real company logs, and real ones are private. `ml/synthetic.py` generates:
  - **normal** behaviour: browsing, logging in, the occasional typo, a rare legitimate admin change;
  - **5 attack kinds**: brute force, credential stuffing, scraping, privilege probing, and "low and slow" (designed to slip under every rule).
- **Fixed random seed** → identical data every run → reproducible model.
- **Splits:** train (normal only), validation (to choose thresholds), test (touched only once, for the final numbers). Measuring on data used for tuning would flatter the model ("data leakage").

### Step 2: Features
A model reads numbers, not events. For one account in one 10-minute window we compute 8 features:
`event_count, failed_logins, successful_logins, denied, api_requests, distinct_event_types, distinct_resources, failure_ratio`.

**Training/serving skew** is a classic ML bug: the model is trained on numbers computed one way, then fed numbers
computed another way in production. We hit it for real:
- live detection checks the window ending at *every* event, including the start of a session;
- training first used only whole windows, so live false alarms were 7% instead of ~1%.

The fix: training now uses the **same** `live_windows()` function as live detection.

### Step 3: The model: Isolation Forest
- **Idea:** build many random trees. Each tree picks a random feature and a random split point, again and again, until every point is alone.
  - **Unusual points get isolated in few splits** (they're far from the crowd).
  - Normal points need many splits (they're surrounded by similar points).
  - Short average path = anomaly.
- **Why it fits:**
  - it needs no attack examples (we train on normal only);
  - it's fast and small (670 KB);
  - it works on a handful of numeric features.
- **Its blind spot, found in our evaluation:** trees **can't extrapolate**. A tree learns "requests > 90" (the busiest normal user), so 400 requests land in the same leaf as 90 and look *normal*. Isolation Forest alone caught 0% of brute force and scraping.
- **The fix: an extreme-value check.**
  - For each feature: how many standard deviations (z-score) above normal is this value?
  - Above the chosen threshold → anomalous.
  - ML-001 = Isolation Forest **OR** extreme-value check.
- **Alternatives:** One-Class SVM, Local Outlier Factor, autoencoders (neural networks). They're heavier or harder to explain, and not clearly better on 8 features.

### Step 4: Thresholds
Every anomaly detector outputs a score. *Where* you draw the line trades false alarms against missed attacks.
- We set a budget: about **1% false alarms on normal activity**.
- Each check gets half of it.
- The thresholds are measured on **validation** normal data.

### Step 5: Evaluation (test set only)

| Metric | Meaning | Why it matters here |
|---|---|---|
| Precision | Of all alarms, how many were real | Low precision = analysts waste time |
| Recall | Of all attacks, how many were caught | Low recall = missed attacks |
| F1 | Balance of the two | One-number summary |
| False-positive rate | Share of normal windows flagged | Directly drives analyst workload |

Current results and the per-attack table: [ml-evaluation.md](ml-evaluation.md).
- ML-001 catches about 91% of the synthetic attacks at about 0.9% false alarms.
- Rules + ML together catch about 94%.
- **Synthetic data is easier than real life**: treat these as a sanity check, not a promise.

## 3. In production (live detection)

`ML-001` is registered next to the rules (`detection/catalogue.py`). On every event, the engine:
1. cuts the account's recent activity into windows (at most 50 checked per event, to bound the work);
2. computes the features;
3. asks both checks;
4. merges overlapping anomalous windows into one detection.

The explanation names the three features furthest from normal:

> *Anomalous activity for bob between 2026-11-24 10:00:00 UTC and 2026-11-24 10:00:42 UTC: a value far above normal
> (21.3 standard deviations > 15.2) (model iforest-v1). Most unusual: failed_logins=8 (normal about 0.1);
> failure_ratio=1 (normal about 0.0); distinct_resources=1 (normal about 3.7). A statistical signal, not proof: check the evidence.*

(That's real output for 8 failed logins in 42 seconds. The threshold, about 15 standard deviations, is high because
normal failed logins are rare, so their standard deviation is tiny.)

Safety:
- If the model file is missing, its features don't match, or scikit-learn isn't installed, ML-001 **switches itself off** and logs a warning. The rules keep working (tested).
- The model must be loaded with the scikit-learn version that saved it, so it's **pinned** (`scikit-learn==1.9.1`).

## 4. Retraining

```powershell
python ml/train.py
```

This regenerates `backend/app/ml/model/` and `docs/ml-evaluation.md`. Same seed → same model.
- Changing features → bump `FEATURE_SCHEMA_VERSION`. The detector refuses a model trained on different features.
- Changing the model → bump `MODEL_VERSION` in `train.py`. New detections record which version produced them.

## 5. Limitations and next steps

- **Synthetic data:** real users are messier. The first step with real data is to measure false alarms and re-tune.
- **One window size and per-account only:** slow attacks over hours, and attacks spread across accounts, are invisible.
- **No feedback loop yet:** analyst verdicts (false positive / true positive) should become labelled training data.
- **Drift:** normal behaviour changes over time (new features, holidays). Retrain on a schedule and watch the alarm rate.

## 6. Interview questions

- *Why Isolation Forest?* Section 2, step 3. Also know its weakness (no extrapolation) and how you covered it.
- *How did you choose the threshold?* A false-alarm budget measured on validation data, never on test data.
- *What's training/serving skew? Did you hit it?* Yes: the 7% vs 1% story in step 2.
- *Can you trust 91% recall?* On synthetic data only. Say why, and how you'd validate on real traffic.
- *Precision vs recall in security?* Missing an attack (recall) vs wasting analysts' time (precision). The threshold sets the trade.
